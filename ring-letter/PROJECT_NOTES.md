# Ring letter MVP

Mobile-first anonymous story reading and submissions. Vinext + D1. All sample stories are marked AI fiction. Only author-consented, manually approved submissions are publicly readable. No AI API calls, messaging, or external analytics.

Public users receive an HttpOnly random session cookie; only its SHA-256 hash is stored. Sessions slide (v2 V3-c, issue #4 §6.2): the cookie lasts one year and is re-issued by worker/index.ts on every response to a request carrying a live cookie (pages and API alike, except routes that set or clear it themselves), and sessions.last_seen is moved forward at most once a day; a session is valid, and kept by retention, until one year after its last visit. Reading pages never creates a session; only writing, submitting and feedback do. 我的片段 offers 在這台裝置登出 (DELETE /api/session: deletes the session row and clears the cookie; the stories, feedback and attempts stay and expire under their own rules; without a session it still clears the cookie and returns 200), for shared devices; a later submission from that browser starts a new identity. Losing the cookie (cleared, other device, more than a year away) loses self-service access: the author emails the public contact address ringletter@wetrytrysee.cc (Cloudflare Email Routing; footer, privacy notice and 我的片段) with the title, part of the text or the approximate date, and an admin deletes the story in /admin (rather delete too much than too little), usually within 7 days, and replies. Retention (v2 V3-a, issue #4 §6): a daily Cron Trigger (lib/server/retention.ts) deletes expired rows; creating a session no longer purges anything, and reads apply the same windows. Stories keep the terms of the consent version they were submitted under (prefix of stories.consent): under the old "30 days" wording (v2-2026-11-05, legacy or empty), every story, approved included, is hidden and deleted 30 days after creation, and later status changes never extend that; under a version in PERMANENT_CONSENT_VERSIONS (v3-2026-11-12), approved stories are never deleted automatically (only by withdrawal, erase-all or admin delete) and other statuses expire 30 days after their last status change (status_at). Since V3-c every new submission uses v3-2026-11-12, whose consent wording says so (components/write/ConsentFields.tsx); earlier stories keep their stored consent string and their 30-day terms, nothing is migrated. Deleted stories take their feedback and consent history with them; feedback and writing attempts expire 30 days after creation, sessions one year after last_seen, admin_events one year after creation. Consent history is kept in the append-only consent_events table (one row per submit/share/unshare, with the consent wording version) and is deleted with its story. Limits are per session, not a bot-defense guarantee.

API (v2, REST, no compatibility with the v1 /api/letter actions): public GET /api/stories, POST /api/session and DELETE /api/session (log out on this device); anonymous-session POST /api/writing-attempts, POST and GET /api/me/stories, DELETE /api/me/stories/:id, PATCH /api/me/stories/:id/sharing, DELETE /api/me, POST /api/feedback; admin (v2 V6-a/V6-b, issue #4 §5.2; the old GET /api/admin/queue with its 200-story cap is gone) GET /api/admin/summary, GET /api/admin/stories (status, reshare, consent v2/v3, expiring, q, Taipei from/to, id; 50 per page by cursor; same retention rules as every read; each row with expiresAt, terms and feedbackCount), POST /api/admin/stories/:id/moderation, GET /api/admin/feedback, DELETE /api/admin/feedback/:id, POST /api/admin/moderation (batch reject or delete, per-story results, never batch approval) and GET /api/admin/events. Admin operations (approve, reject, delete story, delete feedback) are logged in admin_events with the verified Access email, the action, the target id and the time, never content, titles or sessions; a row is written in the same batch as the change and only when the change happens, survives the deletion of its story, and is deleted after a year (stated in the privacy notice). Author withdraw and erase-all are not logged. Every POST, PATCH and DELETE is same-origin checked. Admin access: the admin UI is /admin and the admin API lives under /api/admin/. In production both are behind a Cloudflare Access application, and the Worker independently verifies the Access JWT and requires the email to be in the ADMIN_EMAILS secret (lib/server/auth.ts, lib/server/access-jwt.ts); missing config denies all admin requests. Plan and progress: GitHub issue #2. In `npm run dev` there is no Access: an identity is only granted to requests carrying the per-run dev secret (.wrangler/dev-admin-token), never based on source address, because tunnels and port forwards arrive from loopback. Anonymous sessions can submit at most 5 stories, 30 feedback events, 30 writing starts and 10 sharing changes per day. Sharing is not fixed at submission (v2 V3-b, issue #4 §6.1): in 我的片段 the author can ask to share a private or rejected story (改為分享 / 再次申請分享: the three consent boxes, current wording, ticked again; the story moves onto the current consent version and goes back to pending, never reusing an earlier approval) or stop sharing a pending or approved one (停止分享: private at once, off the public list, approved_at cleared, consent version kept). Any other combination is 409; each story may ask to share at most 3 times after submission (share events in consent_events), after which the button is disabled but stop sharing and withdraw remain. Each change writes a share/unshare consent event and sets status_at, so a story that stopped sharing expires under its consent version's rule for non-approved stories. The admin story list marks pending stories that asked again (「重新申請分享」) with their consent history count, and the admin UI sends each decision with the statusAt it displayed: an approval or rejection of a story that changed since (e.g. stopped and re-shared) is refused with 409, so nothing is approved unseen; the UI then re-fetches only that story, updates its card in place and says 「這篇剛剛改變了，請再看一次」 (no full reload, filters and scroll kept). Admin UI (V6-b): summary → filters → story list → feedback → operation log. The filters live in the URL (/admin?status=…&reshare=1&consent=v2|v3&expiring=7&q=…&from=…&to=…&id=…), so reload, back/forward and shared links keep them; a story id pasted into the search box becomes an exact id lookup in all statuses. Cards show the story id, submission date, consent version and 剩 N 天 (none for stories kept until withdrawn), for checking a deletion request; after a delete the notice quotes 已刪除《title》（date）. Feedback can be filtered by kind and by story (a card's 看回饋（N）), shows the story title from the API (demo stories as 示範故事), links to the story's card, and can be deleted one at a time after a confirm. The operation log can be filtered by admin; live stories link to their card, gone targets show （已刪除）. Batch actions (V6-c): every card has a checkbox; 不通過或下架 sends only the ticked pending/approved stories (disabled with the reason when none are ticked) and 永久刪除 sends all ticked ones; there is never a batch approval, since every story must be read before it goes public. 全選 ticks only the loaded cards, a filter change clears the selection, and more than 50 ticked is refused with a message instead of being cut short. A confirm lists the count and the first titles. Each story is sent with the statusAt/consentEvents its card showed and gets the single-story rules: done deletes leave the list, done rejections are re-fetched in place; refused ones stay ticked with the reason on the card (剛剛改變了 / 這個狀態不能不通過 / 已不存在) and are re-fetched (gone ones leave the list), and a notice sums it up (已永久刪除 N 篇；M 篇未處理（…）). Private stories cannot be approved. No admin text editing: changed author consent would otherwise be needed.

Browser QA and API checks are local. tests/api.mjs uses the dev-only admin identity header ONLY against the local dev server (production builds compile that path out); never enable any header-spoofing convenience route in production. Test stories are removed after tests.

Before wider release: add stronger abuse prevention, recoverable author identity if needed (a private per-story management link is the next step if admin-assisted deletions become frequent), scoped reviewer membership, and a real author content library. Readership is not automatically measured: feedback counts are events, not unique people or retention.

## Human cross-time matching pilot (2026-11-05)

The home page and default reading experience use components/reading/MatchExperience.tsx and data/matching.ts, with no API requests, cookies, database writes, matching algorithm, or third-party analytics. Existing legacy submissions/database are retained; footer links explicitly expose prior submissions/withdrawal and the prior public inbox. Never reuse old consent for the new manual matching process.

Update FORM_URL_DISTRESS and FORM_URL_ECHO at the top of data/matching.ts to activate external forms. Both currently equal '#'; clicking them shows an unavailable message, not a fake submission. Forms should supply the contact/removal path mentioned in the UI, separately collect receiving-match consent and future de-identified reuse consent, and identify the letter being echoed. Echo does not automatically send to an author.

MATCH_LETTERS holds eight fictional samples (two per SCENARIOS category). Replace id, scenario, year, situation, matchReason and body; set isExample=false only for consented, reviewed, de-identified real letters. These bundled letters are publicly readable; do not place confidential source originals here. Keep at least two letters per scenario for the next-letter interaction. Match reasons are authored copy, not computed personalization.

Browser QA: all four scenario buttons opened their first letter and next switched to the second letter in the same scenario. Both '#' form links displayed explicit unavailable notices; event attributes were verified. Home and reader had no horizontal/text overflow at 320, 390, 768, 1024, 1440 CSS pixels. TypeScript and production build passed. Data-event hooks are present only; there is no persistent event count yet.
